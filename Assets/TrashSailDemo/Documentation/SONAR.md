# Sonar implementation and limitations

`DemoSonarPerception` configures the installed MARUS `Sonar3D` before Start. The default is 96 horizontal by 9 vertical rays, 128 range bins, 110° horizontal and 35° vertical coverage, 0.18–16 m, 8 requested samples/s. It reuses MARUS's completed polar `sonarImage`, with bearing along texture X and range along texture Y. The upstream Cartesian preview remains generated at modest 96×128 resolution but is not used for decisions. No paid assets or ROS are involved.

The model is an approximate simultaneous multibeam geometric ray fan. The first collider along each ray occludes geometry behind it. MARUS rejects hit points above its fixed water level Y=0 and hits below minimum range; the water visual must have no collider. Source `OnSonarHit` models intensity from incidence angle, not validated acoustic scattering. There is no validated fish classifier: every extracted contact is **UNKNOWN**. Exact collider IDs, ClassId, InstanceId, annotations, world object references and resolved elevation are absent from the operational contract.

Completion is detected by `sonarImage.updateCount`, incremented when MARUS's `ComposePolarImage` calls Apply. Allocation and unchanged images are not observations; the generic `hasData` flag is never used. MARUS has no public scheduling/completion timestamp. This adapter conservatively timestamps one requested sample interval before observing a changed texture and uses the previous rendered pose, adding movement since that pose to positional uncertainty. This is an explicit timing approximation, not an exact hardware timestamp. Long scheduling stalls beyond one sample interval would need an upstream timestamp callback for strict age bounds.

Source noise and grid decoration are disabled. The adapter copies only the completed greyscale polar image, applies seeded bounded additive intensity noise once, and exposes that **same** degraded float array to extraction and the colour-mapped preview. `SonarDropout` is per-completed-frame loss probability. Lost frames do not advance operational sequence or freshness; `FreezeFeed` also discards pending delivery and leaves the last displayed frame ageing. Configurable latency uses one pending slot: new source images are dropped while occupied, never queued unboundedly. `ProcessingHz` is measured delivered samples per simulation second. Actual rendering/throughput belongs in the integrated run report.

Echo extraction thresholds intensity (default 0.12) and finds 8-connected range/bearing components. Range is the intensity-weighted bin-centre estimate, and bearing uses the configured equiangular beam coordinates. `LateralExtent` and `RangeExtent` are measured cluster half-sizes in metres and survive into each contact track separately from positional uncertainty. They let association reject a merged/oversized echo rather than treating position agreement as identity. Vertical fan ambiguity is bounded by `range * (1 - cos(verticalFov / 2))`; the exported position lies on XZ, with no invented depth. One-cell echoes remain detectable; weak/missed echoes depend on intensity, resolution, dropout and threshold.

The tracker matches predicted positions greedily, smooths a bounded velocity estimate, assigns perception-local IDs and ages missed contacts for `TrackMemory` seconds (default three). Uncertainty grows 0.35 m/s without an observation. The mission must account for age/uncertainty and must not interpret a disappeared or out-of-fan contact as clearance. The preview shows UNKNOWN IDs, range references, bearing centre and stale/live status; no annotation overlays are enabled.

## Wiring and geometry

1. Place the sonar at Y≈−0.25 m, just ahead of the foremost hull collider, facing +Z with no parent negative scale.
2. Add `DemoSonarPerception`, assign the shared config before Start, and optionally assign an existing `Sonar3D` on that mount. `ConfigureSource()` creates one if absent. Assign `OwnStateProvider` to the vessel's `IOwnStateSource` component to export estimated sensor poses using the calibrated mount offset. When absent, `PoseMode` explicitly reports ideal sensor pose. Configured state noise and latency add to contact uncertainty.
3. Set `Physics.queriesHitTriggers = false` in the demo bootstrap so the intake trigger is not an acoustic wall. This does not disable physical trigger events. MARUS's ray helper has no per-sensor mask; the hull is excluded geometrically by the forward mount and forward-only fan. Verify this in rendered integration.
4. Do not resize MARUS ray geometry live: its native arrays and projection LUT are allocated at Start. Noise/dropout/latency can change live. Reset clears the adapter's tracks, pending frame, counters, preview and RNG, then suppresses two sample periods to discard pre-reset source work.

## Upstream inspection findings

The installed `Sonar3D.OnSonarHit` dots a local ray direction with a world hit normal; this can incorrectly change echoes after heading changes. The lead is applying a coordinated source fix to rotate the ray before taking the incidence dot product and clamp that dot product to [−1,1]. Because the callback executes inside `ReadbackDataJob`, the rotation must be cached on the main thread rather than fetching `transform` inside the job. The adapter does not alter upstream code. Upstream `RaycastJobHelper.Dispose` also leaves the static callback dictionary entry, and `SensorSampler` retains disabled callbacks; reuse the same sensor across resets rather than repeatedly creating/destroying it. Source annotation textures are allocated by MARUS even with no annotation saver, but the adapter never reads them.

## Validation scope

`Tests/SonarTests.cs` covers beam/bin conventions, transformed projection and absence of elevation, seeded noise and display equivalence, separate returns, extended-contact uncertainty, temporal identity/ageing and reset. The lead runs Unity EditMode and the rendered sensor scenarios in the single coordinated editor/player. Worker fixture tests alone do not establish real sonar cadence, scene geometry, fish avoidance or rendered performance.

Extraction connects adjacent bearing samples across one missing range bin when the two-bin centre spacing is at most 0.25 m (0.2472 m at the default resolution). This accommodates intensity fragmentation on curved surfaces. It does not identify the reflecting object: distinct objects inside this resolution can remain unresolved. The connected component retains its full measured range/bearing extent and uncertainty, allowing the mission's existing size interlock to reject broad merged returns. Two missing range bins or a bearing gap remain disconnected. The `OneMissingRangeBinJoinsFragmentsAndPreservesCombinedExtent` fixture covers joining, centroid, retained width and independent contacts. Runtime and test assemblies compile with the installed Unity Roslyn compiler; fixture execution and rendered regression belong to the serialized Unity integration run.
